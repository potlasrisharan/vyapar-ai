# Review checklist

Use this when auditing existing UI against the HIG. Work top to bottom — the first three sections catch most real problems. Report findings as **file:line → what's wrong → the HIG rule → the fix**, ordered by severity.

**Severity guide**
- **Blocking** — fails accessibility minimums, gets rejected by App Review, loses data, or misuses an Apple asset.
- **High** — makes the app feel non-native or actively confuses people.
- **Medium** — deviates from guidance without a stated reason.
- **Low** — polish.

---

## 1. Accessibility (blocking unless noted)

- [ ] Every interactive element meets its platform's minimum size (iOS/iPadOS/watchOS 44×44 pt · macOS 28×28 pt · tvOS 66×66 pt · visionOS 60×60 pt), with ~12 pt padding around bezeled elements and ~24 pt around unbezeled ones.
- [ ] Text meets 4.5:1 contrast up to 17 pt, 3:1 at 18 pt or bold — in **both** appearances.
- [ ] Nothing is conveyed by color alone. Every color-coded state also carries a shape, icon, text, or position.
- [ ] Dynamic Type is supported and the layout survives the largest accessibility size — no overlapping, no unrecoverable truncation, hierarchy preserved.
- [ ] Every meaningful image, icon, and custom symbol has an alternative text label; decorative images are excluded from VoiceOver.
- [ ] Related elements are grouped so VoiceOver reads them together; layout and content changes are announced.
- [ ] Reduce Motion is honored: no bounce, no z-axis depth animation, positional transitions replaced with fades, no animating into or out of blurs.
- [ ] Increase Contrast and Reduce Transparency have been tested — separately and together.
- [ ] Every gesture has a non-gesture alternative. No custom multi-finger or multi-hand gesture for a common action.
- [ ] Full Keyboard Access reaches everything; no system shortcuts are overridden.
- [ ] Media has captions, subtitles, audio descriptions, or a transcript as appropriate.
- [ ] Charts have per-element (or per-group) accessibility labels; axis and tick labels are hidden from assistive technologies.
- [ ] Nothing auto-dismisses on a timer that people need time to read or act on.

## 2. Privacy and trust (blocking)

- [ ] Permissions are requested at the moment the feature needs them, not at launch — unless the app can't function otherwise.
- [ ] Every purpose string is a complete sentence, active voice, sentence case, ending period, stating how and why.
- [ ] Any pre-alert screen has exactly one button labeled Continue or Next — no Allow, no Cancel, no close, no incentive, no imitation of the system alert.
- [ ] Only the minimum data is requested; optional data is clearly optional and declining it doesn't lock anyone out.
- [ ] Secrets are in the keychain, never in plain text.
- [ ] If people can create an account in-app, they can delete it in-app (or through a directly linked page).
- [ ] Nothing sensitive appears in a notification, a Live Activity, a widget, a complication, or an Always-On display.
- [ ] AI-generated content is disclosed; nothing implies a human wrote it.

## 3. Apple assets and trademarks (blocking)

- [ ] Apple Pay, Sign in with Apple, Add to Apple Wallet, Verify with Wallet, and ID Verifier buttons come from the Apple APIs — not recreated.
- [ ] The AirPlay, HomeKit, and Apple Health icons are Apple-provided, unaltered, and noninteractive, with the required clear space.
- [ ] The Apple Pay mark is never used as a button.
- [ ] App Clip Codes are generated by App Store Connect or the generator tool, unmodified, with correct clear space and minimum size.
- [ ] Activity rings show only Move, Exercise, and Stand, unmodified, on black, for one person, never as decoration or branding.
- [ ] SF Symbols aren't used in app icons, logos, or trademarked contexts; noncustomizable Apple product/feature symbols aren't customized.
- [ ] No replicas of Apple hardware anywhere.
- [ ] Apple trademarks are never translated, pluralized, or made possessive, and don't appear in the app name or images.
- [ ] "Hey Siri" translations translate only "Hey."

## 4. Platform fit

- [ ] The layout is designed for *this* platform's ergonomics, viewing distance, and input model — not scaled from another.
- [ ] Content extends to the display edges; controls float above it rather than sitting in the same plane.
- [ ] Safe areas and layout margins are respected — Dynamic Island, camera housing, corner radii, tvOS overscan (60 pt top/bottom, 80 pt sides).
- [ ] macOS: every toolbar item exists as a menu bar command; standard menus appear in the standard order; nothing critical sits at the window's bottom edge.
- [ ] iPadOS: windows resize fluidly through the full range; compact layouts are deferred as long as possible; leading toolbar buttons don't collide with window controls.
- [ ] tvOS: every element is reachable by directional focus; assets exist at the focused size; system focus effects are used.
- [ ] visionOS: content stays within window bounds; buttons are ≥60 pt apart center-to-center; glass backgrounds are retained; no head-anchored content; no peripheral motion.
- [ ] watchOS: navigation is anchored to the Digital Crown *and* backed by touch; content is edge to edge; no more than two or three side-by-side controls.

## 5. Component choice

- [ ] Alerts carry critical, actionable information — not status, not startup information, not warnings about expected reversible data loss.
- [ ] Action sheets, not alerts, present choices related to an intentional action.
- [ ] Only one modal view is visible at a time; no cascading popovers; no view above a popover except an alert.
- [ ] Every modal view has an obvious, platform-conventional dismissal, and confirms before discarding user-generated content.
- [ ] The tab bar is for navigation only, always visible, with no disabled or hidden tabs.
- [ ] Toolbars hold actions; navigation and critical actions are in dedicated groups; there are no more than about three groups; text-labeled buttons are separated by fixed space.
- [ ] Pop-up buttons present mutually exclusive options; pull-down buttons present actions.
- [ ] Context menu items are duplicated in the main interface; unavailable items are hidden, not dimmed.
- [ ] Progress indicators are determinate where the duration is knowable, keep moving, and never switch between bar and spinner styles.
- [ ] Custom controls that behave like system controls look and behave exactly like them — or are clearly different.

## 6. Buttons and actions

- [ ] Every custom button has a press state.
- [ ] At most one or two prominent buttons per view.
- [ ] The preferred choice is distinguished by style, not size.
- [ ] No destructive action carries the primary role.
- [ ] Alerts with a destructive action include a Cancel button; Cancel is never the default.
- [ ] Button titles are specific ("Erase", "Delete", "Convert") rather than "OK", "Yes", or "No" — except in a purely informational alert.
- [ ] The most likely choice is trailing in a row, top in a stack; Cancel is leading or bottom.
- [ ] No primary action is buried in a More menu.

## 7. Color, materials, and motion

- [ ] System colors are used where they exist; no system color values are hard-coded; no semantic color is repurposed.
- [ ] Every custom color has light, dark, and increased-contrast variants.
- [ ] There is no app-specific light/dark appearance setting.
- [ ] Liquid Glass is confined to the functional layer, used sparingly on custom controls, with the correct variant (regular for text-heavy, clear only over rich media with a 35% dim over bright content).
- [ ] Colored Liquid Glass is limited to genuine emphasis, at most one control per view.
- [ ] Scroll edge effects — not backgrounds — separate bars from content, one per view, preferring the automatic style.
- [ ] Motion has a purpose; frequent routine interactions aren't animated; nothing blocks input during a transition.
- [ ] Motion is never the only channel for important information.

## 8. Typography and icons

- [ ] Type meets platform default and minimum sizes; Ultralight, Thin, and Light are avoided.
- [ ] The number of typefaces is minimal; a custom face is paired with the system font for body and captions.
- [ ] Text styles are used rather than hard-coded sizes; symbolic traits handle emphasis and leading.
- [ ] Interface icons share size, detail level, stroke weight, and perspective, and are optically (not geometrically) centered.
- [ ] Standard actions use the standard SF Symbols.
- [ ] Custom interface icons are vector (PDF or SVG).
- [ ] App icon layers are unmasked, edges are clearly defined, and no custom highlights, shadows, blurs, or glows fight the system effects.
- [ ] Text doesn't appear in the app icon, the launch screen, an App Clip card image, a pass image, or a Top Shelf sectioned row image unless the guidance explicitly allows it.

## 9. Writing

- [ ] Buttons and links start with a verb; no "Click here."
- [ ] Copy addresses people as *you*; *we* is absent, especially from errors.
- [ ] Capitalization style is consistent per element type.
- [ ] Errors say what to do, not just what went wrong; no "Oops."
- [ ] Device-appropriate verbs — *tap* on touch, *click* on Mac.
- [ ] No jargon, colloquialisms, humor, or unnecessary gendered language.
- [ ] Alert titles describe the situation; informative text adds value or isn't there.
- [ ] Empty states guide people to a next action.
- [ ] Text fields have labels and format hints; errors instruct rather than scold.

## 10. Patterns

- [ ] The launch screen matches the first screen, with no text, no logo, and no branding.
- [ ] Onboarding is brief, optional, interactive, and skippable-once.
- [ ] The previous state is restored granularly on relaunch.
- [ ] Loading shows something immediately and lets people do other things.
- [ ] Search scope is visible; suggestions and recents are offered; history can be cleared.
- [ ] Settings offer good defaults, are minimal, don't duplicate system settings, and put task-specific options in the screens they affect.
- [ ] Undo works multiple times, describes its target, and shows its result.
- [ ] Ratings are requested only after demonstrated engagement, never during onboarding or a task, with at least a week or two between requests, using the system prompt.
- [ ] Notifications are concise, non-repeating, correctly leveled (Time Sensitive only for the moment; never for marketing), and don't instruct people to go do something in the app.
- [ ] Drag and drop has a menu-based alternative, shows a translucent drag image, indicates whether a destination accepts the content, and can be undone.

---

## Reporting

For each finding:

```
[Severity] file:line
What: <the specific problem>
Rule: <the HIG guidance it violates>
Fix: <the concrete change, with Apple's numbers where they apply>
```

If a deviation from the HIG appears deliberate and well-reasoned, say so and move on — the guidelines are tools for weighing competing priorities, not a compliance regime. Flag it only if the deviation costs accessibility, clarity, or trust.
